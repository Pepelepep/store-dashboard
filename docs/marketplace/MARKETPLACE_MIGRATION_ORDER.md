Audited on 2026-07-19 from the migrations present on `marketplace/phase-7p-existing-store-upgrade-validation`. Apply them in the exact order below and never edit a migration that has already run. The repository has no authoritative deployment ledger and this environment does not expose `supabase_migrations.schema_migrations`, so **applied status cannot be proven from Git**. “Required/current” means the current application depends on the object; run `PHASE_7P_PREFLIGHT.sql` against the marketplace database to establish its actual state before applying anything.

The two un-timestamped `20260618` job-type migrations replace the same check constraint. In filename order the reconciliation migration temporarily removes `financial_backfill_30d`. **Do not deploy or run workers from that intermediate state. Execution must continue through `20260713120000_sync_automation_and_retention.sql`, which restores the complete current job-type set, before Phase 7P is applied.**

## Verification SQL

Run the full preflight first. These focused checks support the table references above:

```sql
-- V1: required relations
SELECT name, to_regclass('public.' || name) AS relation
FROM (VALUES ('shops'),('orders'),('order_lines'),('sync_jobs'),('webhook_events'),
 ('staff_people'),('staff_identity_aliases'),('pos_attribution_setup'),
 ('sync_automation_state'),('maintenance_tick_state')) v(name);

-- V2: columns
SELECT table_name, column_name FROM information_schema.columns
WHERE table_schema='public' AND table_name IN
 ('orders','order_lines','user_location_access','sync_automation_state','pos_attribution_setup')
ORDER BY table_name, ordinal_position;

-- V3: indexes and uniqueness
SELECT indexname, indexdef FROM pg_indexes WHERE schemaname='public'
ORDER BY indexname;

-- V4: callable RPC signatures
SELECT p.oid::regprocedure FROM pg_proc p JOIN pg_namespace n ON n.oid=p.pronamespace
WHERE n.nspname='public' ORDER BY 1::text;

-- V5: current job checks (must include full_refresh and financial_backfill_30d)
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
WHERE conrelid='public.sync_jobs'::regclass AND contype='c';

-- V6: service-role grants
SELECT grantee, privilege_type FROM information_schema.role_table_grants
WHERE table_schema='public' AND grantee='service_role' ORDER BY table_name, privilege_type;

-- V7: duplicate identity safety
SELECT shop_domain, lower(email), count(*) FROM public.staff_people
WHERE email IS NOT NULL GROUP BY 1,2 HAVING count(*) > 1;
SELECT shop_domain, alias_type, alias_value, count(*) FROM public.staff_identity_aliases
GROUP BY 1,2,3 HAVING count(*) > 1;

-- V8: current view
SELECT pg_get_viewdef('public.staff_pos_seller_metrics'::regclass, true);

-- V9: exact permission duplicates (must be empty before #26)
SELECT shop_domain, lower(btrim(user_email)), coalesce(btrim(shopify_user_id), ''),
       coalesce(btrim(shopify_location_id), ''), count(*)
FROM public.user_location_access WHERE user_email IS NOT NULL
GROUP BY 1,2,3,4 HAVING count(*) > 1;
SELECT shop_domain, btrim(shopify_user_id), coalesce(btrim(shopify_location_id), ''), count(*)
FROM public.user_location_access WHERE shopify_user_id IS NOT NULL
GROUP BY 1,2,3 HAVING count(*) > 1;
```

## Safe application procedure

1. Take a database snapshot and run the Phase 7P baseline for the target shop.
2. Run `PHASE_7P_PREFLIGHT.sql` before Phase 7P. Resolve every `BLOCKED` prerequisite; never treat the absence of a migration ledger as permission to replay `001`.
3. If historical prerequisites are missing, apply only the reviewed missing sequence in filename order. Never stop between the two `20260618` constraint replacements and `20260713120000_sync_automation_and_retention.sql`.
4. Apply `20260717120000_existing_store_upgrade_hardening.sql`. It must fail rather than delete or rewrite duplicate permissions.
5. Deploy/open the Phase 7P app once, then run `PHASE_7P_POSTFLIGHT.sql`. Continue only on `GO` or an explicitly accepted warning; any `BLOCKED` result stops the pilot.
