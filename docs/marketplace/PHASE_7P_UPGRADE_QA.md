# Phase 7P existing-store controlled-pilot QA

Use one authorized colleague store. Before starting, record the operator, UTC start time, app commit, database target and exact `shop_domain`. Every SQL file has one target parameter; set it to that same domain.

## Global stop rule

Stop immediately and follow `PHASE_7P_ROLLBACK.md` after any `BLOCKED` result, unexpected tenant/domain, migration error, unhandled application error, access loss, duplicate increase, unexplained data decrease, destructive rewrite or unexplained financial drift. Do not proceed merely because a later step might repair an earlier failure. A `WARNING` may proceed only after its cause and operator acceptance are written in the pilot record.

## Exact ordered checklist

1. **Confirm isolation and recovery.** Confirm the colleague store, marketplace preview app, Supabase project and Prisma database are the intended pilot targets; pause overlapping manual work; take the approved database snapshot. **Continue only if:** target identities and restore owner/location are recorded. **Stop if:** any target is ambiguous or recovery is unavailable.
2. **Run preflight before Phase 7P.** Set the one target in `PHASE_7P_PREFLIGHT.sql`, run it read-only and save the complete result. **Continue only if:** summary is `GO`. **Stop if:** summary is `BLOCKED`; review and explicitly accept any `WARNING` before continuing.
3. **Capture the SQL baseline.** Set the same target in `PHASE_7P_BASELINE.sql`, run it read-only and save raw output. Run its separate read-only Prisma session query against `DATABASE_URL`. **Continue only if:** the shop identity, entity counts, financial values, access rows and operational counts are captured without query errors. **Stop if:** the placeholder remains, the tenant differs or a required metric is unavailable without an explicit `UNAVAILABLE`/coverage note.
4. **Capture the V0 UI baseline.** Record date range, timezone, order count, net sales, discounts, refunds, COGS and profit; save Profit Dashboard and Location Performance screenshots. **Continue only if:** the reference is reproducible and any SQL/UI formula difference is explained. **Stop if:** there is no reliable before-state.
5. **Bring historical schema to the prerequisite state, if needed.** Apply only missing additive migrations in `MARKETPLACE_MIGRATION_ORDER.md` order. The 20260618 job-type constraint replacements are an unsafe intermediate state: once that sequence starts, continue through `20260713120000_sync_automation_and_retention.sql` before deploying or running workers. **Continue only if:** every required historical migration completes and a fresh preflight is `GO`. **Stop if:** any migration fails or preflight is not `GO`.
6. **Apply only the Phase 7P migration.** Apply `20260717120000_existing_store_upgrade_hardening.sql`. **Continue only if:** the migration completes. **Stop if:** either strict permission index reports duplicates or any statement fails; investigate without deleting or automatically cleaning permission rows.
7. **Open the upgraded marketplace app once.** Complete OAuth/reauthorization for the existing store and wait for the app shell. **Continue only if:** there is no OAuth loop, unexpected billing, scope expansion or unhandled initialization error. **Stop if:** the wrong app/store/database is reached or initialization fails.
8. **Run final-state postflight.** Set the same target in `PHASE_7P_POSTFLIGHT.sql`, run it read-only and save the complete result. **Continue only if:** summary is `GO`, or every `WARNING` has an understood cause and explicit operator acceptance. **Stop if:** any `BLOCKED` result appears.
9. **Verify preserved shop and permission identity.** Compare `shops.id`, the single shop row and all permission grants with the baseline; test owner/admin and an existing manager. **Continue only if:** the internal shop ID is unchanged, there is one logical shop and all prior grants behave identically. **Stop if:** identity changed, a shop duplicated, access was lost or bootstrap access bypassed established permissions.
10. **Verify retry/idempotency behavior.** Reload and open several tabs, then rerun postflight. **Continue only if:** `marketplace_initialized_at` remains set, optional setup state is not overwritten, no populated-store `initial_setup` rebuild appears and at most one full operation is active. **Stop if:** merchant state changes, initialization repeats destructively or jobs duplicate.
11. **Start one Rebuild data operation.** Accept the advanced warning once and record the job ID. **Continue only if:** exactly one `full_refresh` is created/reused, begins with locations and carries full-history order progress. **Stop if:** confirmation is absent, another active full operation appears or reporting tables are pre-cleared.
12. **Let maintenance complete the rebuild with the browser closed.** Record cursor/job transitions and stale-recovery behavior. **Continue only if:** the same job advances to success without browser ownership and retries remain bounded. **Stop if:** it stalls, resets progress, gains concurrent owners or enters a job storm.
13. **Re-run baseline and postflight.** Use the identical domain, date/time assumptions and saved queries. **Continue only if:** postflight is acceptable and shop, Shopify-ID, permission and financial comparisons have no unexplained loss, duplication or drift. **Stop if:** any global stop condition occurs.
14. **Run Sync now twice and overlap one request with cron.** Record returned job IDs. **Continue only if:** the active `full` is reused/claimed once and completed counts do not inflate. **Stop if:** more than one full/full_refresh is active or reporting identities duplicate.
15. **Create one traceable non-POS Shopify order.** Wait for webhook/cron processing with the UI closed. **Continue only if:** the event is deduplicated, reaches a terminal successful state and exactly one order with the expected lines/financials appears. **Stop if:** manual queue action is required, the order is missing/duplicated or financial values are inconsistent.
16. **Configure the POS tile explicitly.** Complete Staff/POS onboarding. **Continue only if:** `tile_confirmed_at` changes only after confirmation and historical orders/permissions remain unchanged. **Stop if:** setup was pre-confirmed or old attribution/access mutates.
17. **Complete one attributed POS sale.** Record seller, location and device. **Continue only if:** the new lines carry expected V2 attribution, appear once and do not grant dashboard authorization; old unstamped lines remain Unassigned. **Stop if:** historical rows change or seller identity grants access.
18. **Validate staff and access lifecycle.** Test unmapped state, V1/V2 identity metadata, a manager who is also a seller, then remove and restore one test manager grant. **Continue only if:** people/aliases stay unique, suggestions are deterministic, access follows only `user_location_access` and attribution/history persists. **Stop if:** aliases duplicate, attribution controls authorization or removal destroys business history.
19. **Validate both dashboards.** Using the original date range/timezone, compare Profit Dashboard and Location Performance with the saved baseline and test orders. **Continue only if:** counts, locations, net sales, discounts, refunds, COGS, profit and attribution reconcile with documented Shopify changes. **Stop if:** a location is missing/duplicated or any variance is unexplained.
20. **Observe automation for several hours.** Record multiple maintenance/reconciliation ticks, queued/running/failed jobs and webhook backlog; finish with baseline and postflight. **Pilot passes only if:** final postflight is acceptable, one active full operation maximum is maintained, failures remain diagnosable, backlog drains and saved baselines remain stable. **Stop if:** cleanup is destructive, failures are silent, repeated rebuilds occur or any global stop condition appears.

Do not mark the pilot complete until the operator, reviewer and accepted warnings are recorded alongside the final baseline and postflight outputs.
